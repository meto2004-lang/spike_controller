# Hyena Control — تطبيق التحكم بروبوت SPIKE Prime (Pybricks)

تطبيق مكتمل للتحكم بروبوت SPIKE Prime عبر البلوتوث: إرسال/تشغيل/إيقاف البرامج،
استقبال مخرجات الروبوت حيّاً، إدارة الملفات، وتوليد برنامج سباق من بيانات التدريب
المسجّلة. يعمل بواجهتين على المنطق نفسه:

- **واجهة ويب حديثة** على نمط Pybricks Code (`spike_server.py` + `web/`) — موصى بها.
- **تطبيق مكتبي** بـ Tkinter (`spike_controller.py`) — ما زال متاحاً كما هو.


## تطبيق الويب (واجهة شبيهة بـ Pybricks Code)

أصبح للتطبيق واجهة متصفح حديثة على نمط [Pybricks Code](https://code.pybricks.com/):
شريط علوي داكن يعرض حالة الروبوت وزر **«تنزيل وتشغيل»** بارزاً، محرر بعدة تبويبات
مع تلوين صياغة بايثون وأرقام أسطر وإكمال تلقائي وطي كود، لوحة مخرجات قابلة للتحجيم
مع شريط تقدم الرفع، وشريط جانبي للملفات والأمثلة ومولّد السباق، مع دعم كامل
للعربية والإنجليزية (RTL/LTR) ومظهرين فاتح وداكن.

### لماذا خادم محلي؟

المتصفح لا يستطيع تنفيذ بروتوكول Pybricks عبر البلوتوث من دون Web Bluetooth
(وهو متاح في كروم فقط ولا يعمل في متصفحات أخرى). لذلك بقي النقل في بايثون
باستخدام `pybricksdev` نفسه المستخدم في التطبيق المكتبي، وتتصل الصفحة بالخادم
المحلي عبر HTTP و**Server-Sent Events**. النتيجة: واجهة عصرية تعمل في أي متصفح،
وبنفس تسلسل النقل والتحقق الموثّق أدناه.

### التشغيل

```sh
python spike_server.py                 # http://127.0.0.1:8000 ويفتح المتصفح
python spike_server.py --port 9000
python spike_server.py --host 0.0.0.0   # متاح لأجهزة الشبكة المحلية
python spike_server.py --simulate       # دون بلوتوث إطلاقاً (عرض/تجربة)
```

- Windows: انقر `start_web.bat`، وLinux/macOS: `./start_web.sh`.
- لا يحتاج إلى أي حزمة JavaScript خارجية: المحرر (CodeMirror) مُضمَّن داخل `web/vendor/`
  وتعمل الواجهة دون إنترنت.
- إذا لم يكن `pybricksdev` مثبتاً يبدأ الخادم تلقائياً في **وضع المحاكاة**: زر الاتصال
  يوصلك بروبوت محاكاة يعرض مخرجات واقعية، والرفع والتشغيل وشريط التقدم ومولّد السباق
  تعمل كاملة للتجربة والعرض. يظهر وسم `Simulation` في الشريط العلوي دائماً.

### أين توجد الملفات والإعدادات

تستخدم نسخة الويب نفس مجلد بيانات التطبيق المكتبي:

- البرامج: `DATA_DIR/programs` (ملفات `.py` التي تنشئها من الواجهة)
- الإعدادات: `DATA_DIR/spike_web_config.json`
- السجلات: `DATA_DIR/logs` (ومنها `web_transfer_errors.log` عند فشل النقل)

حيث `DATA_DIR` هو `%LOCALAPPDATA%\HyenaControl` على ويندوز أو
`$XDG_STATE_HOME/HyenaControl` على Linux، ويمكن تغييره بـ `HYENA_CONTROL_DATA_DIR`.
يُمكن تحديد مجلد البرامج عبر `--workspace` أو `HYENA_WORKSPACE_DIR`.

| مولّد السباق | يعرض عدد أسطر الجلسة وحالتها، يولّد البرنامج من تسجيلات التدريب، معاينة قبل الفتح في المحرر أو الحفظ، زر جلسة جديدة، وبيانات تجريبية في وضع المحاكاة |
| الإعدادات | اللغة، المظهر، حجم خط المحرر، محاولات الاتصال، مهلة البحث، الاتصال التلقائي، الطوابع الزمنية، التمرير التلقائي، ومسارات المجلدات |

### برمجة الكتل (Blocks)

وضع الكتل يحاكي محرر Pybricks Code:

- من القائمة **ملف ← برنامج بالكتل** (أو زر في لوحة الملفات) يُفتح تبويب كتل جديد.
- كتلة **الإعداد** الصفراء تحدد منافذ المحركات (A/B) والحساسات (C/D)، قطر العجلة، المسافة بين العجلات، وتفعيل الجايرو.
- كتلة **البرنامج** الصفراء ترأس سلسلة التعليمات، والكتل الزرقاء تُسحب من المكتبة أو تُضاف بالنقر.
- كل كتلة تحتوي حقولاً قابلة للتعديل مباشرة (نص الرسالة، الزمن، المسافة، الزاوية، اللون، الجهة).
- كتل التحكم (`كرر`، `إلى ما لا نهاية`، `إذا كان اللون`) تحتوي مساحة داخلية تُفلت فيها كتل أخرى.
- زر **تحويل إلى بايثون** ← ينشئ ملف `.py` جاهزاً، وتبويب **بايثون** داخل نفس التبويب يعرض الكود المولّد لحظياً.
- **تنزيل وتشغيل** يرسل الكود المولّد إلى الروبوت تماماً كملف بايثون عادي.
- يُحفظ البرنامج في ملف `.blocks` (JSON مقروء) ويمكن إعادة فتحه لاحقاً؛ الحدود: 400 كتلة، عمق تداخل 5، نص 200 حرف.

### واجهة الخادم المحلي

| المسار | الوصف |
|---|---|
| `GET /api/bootstrap` | إعدادات، حالة الروبوت، الملفات، الأمثلة، سجل المخرجات |
| `GET /api/events` | بث لحظي (SSE) للمخرجات والحالة وتقدم الرفع ونتائج البحث |
| `POST /api/hub/{scan,connect,disconnect,stop}` | التحكم بالاتصال والبرنامج |
| `POST /api/program/run` | `{code, name, mode: run\|download\|stored, wait}` |
| `POST /api/lint` | تحقق صياغة إرشادي (لا يمنع الرفع) |
| ملفات `.blocks` | تُحفظ وتُقرأ كملفات JSON عادية عبر `GET/POST /api/files/*` |
| `GET/POST /api/files/*` | قائمة/فتح/حفظ/إعادة تسمية/حذف/تنزيل |
| `POST /api/race/preview` | توليد برنامج السباق من جلسة التدريب |
| `POST /api/training/reset` | بدء جلسة تدريب جديدة |
| `POST /api/settings` | حفظ الإعدادات المتحقق منها |

### ملاحظات أمان وحدود

- الخادم يستمع افتراضياً على `127.0.0.1` فقط. عند استخدام `--host 0.0.0.0` يصبح متاحاً
  لأجهزة الشبكة، فاستخدمه على شبكة موثوقة فقط.
- كل طلبات الكتابة تتطلب ترويسة `X-Hyena-Client: web` التي لا تستطيع المواقع الأخرى
  إرسالها عبر نموذج HTML، وهو ما يمنع طلبات cross-site من صفحات خارجية.
- أسماء الملفات تُقبل كأسماء مجرّدة فقط: تُرفض المسارات و`..`، وتُحصر العمليات داخل
  مجلد البرامج، ولا تنفذ الواجهة أي كود على الخادم (التحقق الصياغي لا يُنفّذ البرنامج).
- المحرر لا يعيد تشكيل النص العربي (RTL) داخل الكود؛ الكود يبقى LTR كما في أي محرر
  برمجيات، بينما تُعرض الواجهة كلها في الاتجاه الصحيح.
- فحص الصياغة يستخدم محلل CPython كتقريب لميكروبايثون، ويُستثنى `const(...)` الشائع في
  Pybricks من الخطأ. النتيجة إرشادية فقط، والمرجع النهائي هو مصرف الروبوت.
- التطبيق المكتبي `spike_controller.py` ما زال يعمل كما هو؛ يمكن استخدام أي من الواجهتين
  على المجلد نفسه (لا تشغّل العمليتين متصلتين بالروبوت نفسه في الوقت ذاته).

### لا يمكن الاتصال بالروبوت عبر البلوتوث؟

الاتصال بالبلوتوث يحتاج أن يعمل خادم بايثون **على جهازك نفسه** (أو على جهاز قريب منه)،
لأن المتصفح لا يستطيع فتح اتصال BLE مع SPIKE Prime من تلقاء نفسه. تحقّق من الآتي بالترتيب،
ونافذة «الاتصال بالروبوت» تعرض سبب عدم توفّر البلوتوث في أعلاها:

1. **هل تفتح الواجهة من جهازك؟** إذا كان العنوان في شريط المتصفح ليس `127.0.0.1:8000`
   (مثل نسخة معاينة مستضافة)، فلن يصل التطبيق إلى مستقبل البلوتوث لديك إطلاقاً. شغّل
   `start_web.bat` (ويندوز) أو `./start_web.sh` (لينكس/ماك) على جهازك وافتح
   <http://127.0.0.1:8000>.
2. **هل ثبّتت المتطلبات؟** بدون `pybricksdev` يتحوّل الخادم تلقائياً إلى وضع المحاكاة:
   ```sh
   python -m pip install -r requirements.txt
   ```
   ثم أعد تشغيل الخادم. سجّل الطرفية يطبع سبب تعطيل البلوتوث وطريقة إصلاحه.
3. **هل أعدت التشغيل بدون `--simulate`؟** الخيار `--simulate` يمنع البلوتوث عمداً.
4. **هل الروبوت جاهز؟** شغّله حتى يرمش زر الطاقة بالأزرق، وأبعده عن أي تطبيق آخر متصل
   به (تطبيق SPIKE أو Pybricks Code أو نافذة أخرى من هذا التطبيق).
5. **هل البلوتوث مفعّل على الجهاز؟** على ويندوز تأكد من تفعيل البلوتوث ومن أذونات
   التطبيقات؛ على ماك/لينكس يجب منح إذن البلوتوث للطرفية التي تشغّل الخادم.
6. **جرّب «بحث» أولاً** ثم اختر الروبوت من القائمة بدل كتابة الاسم يدوياً. الأجهزة
   المكتشفة في وضع المحاكاة تظهر بشارة «محاكاة».
7. **سجل الطرفية والمخرجات** يعرض سبب كل محاولة فاشلة، مثل `no hub answered after 6
   attempts (last error: …)`. ملف الأخطاء التفصيلي في `logs/web_transfer_errors.log`.

## تشغيل التطبيق المكتبي (Tkinter)

طريقة 1: انقر مرتين على `start.bat`
طريقة 2: `python spike_controller.py`

يتطلب **Python 3.11 أو أحدث مع Tcl/Tk**. ثبّت الاعتماديات في بيئة معزولة:

```sh
python -m venv .venv
# Windows:
.venv\Scripts\activate
# Linux / macOS: source .venv/bin/activate
python -m pip install -r requirements.txt
python spike_controller.py
```

على Linux قد تحتاج تثبيت حزمة النظام `python3-tk` من مدير حزم توزيعتك.
`start.bat` يستخدم Python الموجود في `.venv` تلقائياً إن وُجد، ويفحص المتطلبات ثم يشغّل التطبيق بالمفسّر نفسه. تبقى نافذة الكونسول ظاهرة لعرض الأخطاء، ويتوقف المشغّل عند الفشل بدلاً من إخفاء المشكلة. تحتاج ميزات USB كذلك تعريفات وصلاحيات مناسبة للمنصة؛ وجود الاعتماديات لا يضمن أن الفرموير يدعم الرفع بالسلك.

## الاتصال بالسلك (USB)

| الزر | الوظيفة |
|---|---|
| **اتصال USB** | يفحص الكابل وواجهات USB — إن وُجدت واجهة Pybricks (0xFF) يتصل ويتحكم بالكامل عبر السلك |
| **استقبال COM** | يفتح منفذ الروبوت (COM) ويعرض أي بيانات يصله في الكونسول مع بادئة `[سلك]` |

> ⚠️ **ملاحظة مهمة:** فيرموير Pybricks الرسمي 4.x لـ SPIKE Prime يعرض على السلك
> منفذ COM فقط (CDC) — **بدون واجهة لرفع البرامج**. هذا مؤكد رسمياً من فريق
> Pybricks: الدعم التجريبي للسلك يتطلب بنناً مخصصاً للفيرموير من
> [labs.pybricks.com](https://labs.pybricks.com/) (تجريبي — غير موصى به قبل المسابقة).
> لذلك **الرفع والتشغيل يتمان عبر البلوتوث**، والسلك متاح للاستقبال والشحن.
> عند تثبيت فيرموير يدعم USB مستقبلاً سيعمل زر «اتصال USB» تلقائياً بكامل وظائفه.

## دورة التدريب الموصى بها

1. اكتب/افتح برنامج التدريب في المحرر ← «إرسال وتشغيل»
2. خذ الروبوت للسجادة ودرّب بالزرار (RIGHT حركة، LEFT حساسان، LEFT+RIGHT حذف)
3. ارجع بالروبوت ← البرنامج ما زال يعمل ← اضغط «بلوتوث» في التطبيق
   (الاتصال فقط لا يمسح التسجيل — تجنب «إرسال وتشغيل» أثناء التدريب!)
4. اضغط «جلسة جديدة / مسح» **قبل** الضغط على CENTER لطباعة تسجيل كامل جديد؛ هذا يمسح بيانات الجلسة السابقة من الذاكرة والعرض بعد التأكيد، ولا يحذف السجلات المحفوظة على القرص.
5. اضغط CENTER في الروبوت ← تظهر جميع التسجيلات في الكونسول
6. اضغط «توليد ملف سباق» ← راجع ← «حفظ كملف» ← أرسله وشغّله

## الملفات

- `spike_server.py` — خادم تطبيق الويب (HTTP + SSE) وتحقّق الصياغة
- `spike_hub.py` — طبقة الاتصال بالروبوت للويب: نقل حقيقي عبر `pybricksdev` وروبوت محاكاة
- `spike_workspace.py` — مجلد البرامج: قائمة/قراءة/حفظ/حذف/إعادة تسمية آمنة
- `spike_race.py` — جلسة التدريب وتوليد برنامج السباق دون واجهة رسومية
- `spike_templates.py` — قوالب البرامج والأمثلة المشتركة
- `spike_paths.py` — مسارات بيانات المستخدم والسجلات المشتركة
- `web/` — واجهة المتصفح: `index.html` و`css/app.css` و`js/` و`vendor/codemirror`
- `start_web.bat` / `start_web.sh` — تشغيل تطبيق الويب بنقرة واحدة

### مكان الإعدادات والسجلات

يُنشأ `spike_controller_config.json` ومجلد `logs/` داخل مجلد بيانات المستخدم:

- Windows: `%LOCALAPPDATA%\HyenaControl`
- Linux/macOS: `$XDG_STATE_HOME/HyenaControl` أو `~/.local/state/HyenaControl`
- يمكن تخصيص المسار بمتغير البيئة `HYENA_CONTROL_DATA_DIR`.

يقرأ التطبيق الإعدادات القديمة الموجودة بجوار البرنامج إذا لم توجد إعدادات جديدة؛ السجلات القديمة لا تُنقل أو تُحذف. استخدم «فتح مجلد السجلات» للوصول إلى المجلد الحالي. أسماء سجلات الروبوت فريدة ولا تستبدل ملفات سابقة.

## تبويبات الملفات

- «جديد» أو `Ctrl+N` أو زر `+` يفتح تبويباً جديداً؛ فتح ملف أو اختياره من الملفات الأخيرة لا يستبدل أي تبويب.
- فتح الملف نفسه مرة أخرى يختار تبويبه الموجود ويحافظ على تعديلاته غير المحفوظة. تُميّز الملفات ذات الاسم نفسه بمسارات المجلدات على التبويبات.
- لكل تبويب نص مستقل وتراجع/إعادة ومؤشر وتمرير وأرقام أسطر وتلوين، وعلامة `*` عند اختلاف النص عن آخر نسخة محفوظة.
- `Ctrl+S` يحفظ التبويب النشط، و`Ctrl+Shift+S` يحفظه باسم جديد. يُمنع الحفظ فوق ملف يمتلكه تبويب آخر مفتوح.
- `Ctrl+Tab` و`Ctrl+Shift+Tab` للتنقل. أغلق بالتقاطع `×` على التبويب أو زر الإغلاق أو `Ctrl+W`؛ تُعرض خيارات حفظ/تجاهل/إلغاء عند وجود تعديلات. إلغاء الحفظ أو فشله يبقي التبويب مفتوحاً، وإغلاق آخر تبويب ينشئ تبويباً نظيفاً.
- عند إغلاق التطبيق تُراجع **كل** التبويبات المعدلة قبل إزالة أي تبويب أو بدء قطع الاتصال. اختيار الإلغاء يبقي التطبيق والاتصال مفتوحين؛ الملفات التي اخترت حفظها قبل الإلغاء تبقى محفوظة.
- الإرسال والتحميل يحفظان التبويب المقصود أولاً ويثبتان مسار الملف للعملية؛ يظهر اسم ملف العملية ومجلده في سطر مستقل أسفل الأزرار حتى عند الانتقال إلى تبويب آخر. تبديل التبويب لا يرسل برنامجاً ولا يوقف الروبوت. الإيقاف وتشغيل البرنامج المخزّن يخصان الروبوت لا التبويب.
- الاتصال والكونسول وبيانات التدريب مشتركة بين التبويبات. هذه المرحلة لا تشمل السحب لإعادة الترتيب أو حفظ الكل أو استعادة التبويبات بعد إعادة التشغيل أو التعطل؛ احفظ الملفات قبل الخروج.

### شريط الأدوات والمساحة المخصصة للكود

- **صف واحد صغير:** بلوتوث، قطع الاتصال، إرسال وتشغيل باللون الأزرق، وإيقاف باللون الأحمر، مع حقل اسم الروبوت/عنوان BLE.
- **قائمة «خيارات»:** اتصال USB، استقبال/إيقاف COM، إرسال مع الانتظار، تحميل فقط، وتشغيل المخزن.
- **قائمة «أدوات»:** توليد ملف سباق، جلسة جديدة/مسح (مع التأكيد عند وجود تسجيلات)، وتصدير السجل.
- تبقى الاختصارات وحالات التعطيل أثناء الاتصال والنقل كما كانت، ويظل الإيقاف متاحاً أثناء الرفع. الأيقونات مرسومة ولا تحتاج خطوط رموز تعبيرية.
- يحصل المحرر افتراضياً على نحو 78٪ من مساحة المحرر/الكونسول، مع كونسول أصغر وفاصل قابل للسحب. تُحفظ نسبة التقسيم عند الخروج. يظهر اسم الملف ومساره القابل للنسخ في صف واحد فوق تبويبات الملفات.
- أُزيلت لوحة معاينة العربية وزرها لتوفير مساحة للمحرر. تبويبات الملفات ودعم العربية في الكونسول والأسماء باقية؛ لا يُعاد تشكيل مصدر البرنامج عند التحرير أو الحفظ. قيد اتجاه العربية المختلطة بالكود في محرر Tk ما زال قائمًا.

### شريط تقدم الرفع

- شريط أخضر رفيع في أسفل النافذة، مع النسبة وعدّاد البايتات في شريط الحالة. يبدأ من الصفر عند إرسال/تحميل ملف جديد، ولا يعتمد على مؤقت أو طول ملف المصدر.
- في بروتوكول الرفع الحديث عبر BLE أو USB المدعوم، تُحسب النسبة من بايتات البرنامج المترجم التي نجح تأكيد كتابتها؛ لا تُحسب ترويسات الحزم أو أوامر البيانات الوصفية.
- يبقى الشريط عند **99٪ كحد أقصى** حتى نجاح أمر إنهاء الرفع والتحقق من جاهزية الروبوت. عند الفشل يصبح أحمر، وعند الإلغاء يصبح بلون تحذيري، مع الاحتفاظ بالتقدم المؤكد دون إظهار 100٪ زائفة.
- تعني **100٪ اكتمال الرفع**، لا انتهاء تشغيل البرنامج. إذا فشل بدء التشغيل أو أُلغي الانتظار بعد اكتمال الرفع، يبقى الشريط ممتلئاً ويُوضّح أن العملية انتهت بخطأ/إلغاء.
- مسارات الرفع القديمة التي لا توفر قياساً مؤكداً تعرض أن النسبة غير متاحة بدلاً من اختلاقها. لا تُضاف إعادة محاولات أو تغييرات على حزم النقل أو أحجامها بسبب شريط التقدم.

### نسخ النص من الكونسول

- النسخ بـ `Ctrl+C` أو `Ctrl+Shift+C` أو زر «نسخ المحدد» أو قائمة الزر الأيمن ينسخ النص المحدد **دون الوقت الذي يضيفه التطبيق أمام الأسطر**، مع الحفاظ على فواصل الأسطر والمسافات.
- يبقى الوقت ظاهراً على الشاشة وفي السجلات كما كان. الأوقات المكتوبة داخل مخرجات الروبوت نفسها لا تُحذف، ولا يتغير النسخ من محرر الكود.

## ضمانات الحفظ والتدريب

- يمكن إدخال اسم الروبوت (كما يظهر في الإعلان) أو عنوان BLE في شريط الاتصال. إن تركته فارغاً تُطلب موافقة صريحة قبل الاتصال بأول روبوت متاح؛ استخدم اسماً مميزاً أو عنواناً عند وجود أجهزة متعددة.

- يظهر اسم الملف المفتوح بوضوح أعلى المحرر وفي عنوان النافذة، ويظهر مساره الكامل في حقل للقراءة فقط يمكن تحديده ونسخه، بدلاً من الاعتماد على شريط الحالة المزدحم.
- تظهر `*` بجوار اسم الملف عند تعديله، وتُحفظ التعديلات قبل الإرسال. فشل الحفظ أو إلغاؤه يمنع الرفع.
- «فتح في تبويب جديد» من نافذة السباق ينشئ وثيقة جديدة غير محفوظة باسم مقترح للسباق، ويترك ملف التدريب وتعديلاته في تبويبه دون استبدال.
- لا تجمع تسجيلات متعددة في جلسة واحدة. إعادة طباعة التسجيل الكامل داخل الجلسة تضيفه مرة أخرى؛ التكرارات قد تكون مقصودة ولذلك لا تُحذف آلياً.
- يفصل المولّد بيانات التدريب الخام عن رسائل التطبيق وعن بادئة `[سلك]` المرئية.
- عند فقد بيانات بسبب الانقطاع غير المتوقع أو ازدحام الاستقبال أو تجاوز الحدود يُمنع التوليد حتى بدء جلسة جديدة واستقبال التدريب كاملاً. قطع الاتصال عمداً بعد اكتمال الاستقبال لا يُبطل بيانات التدريب المكتملة.
- انتظر اكتمال الاستقبال ومعالجة الرسائل قبل التوليد. وصول مخرجات جديدة يُبطل المعاينة القديمة حتى داخل الجلسة نفسها، ويُلزم تحديثها. يُعاد التحقق بعد نافذة اختيار ملف الحفظ وقبل فتح تبويب السباق، لمنع استخدام معاينة أصبحت قديمة.
- المولّد يقبل أوامر حرفية فقط: `robot.straight(distance)` و`robot.turn(angle)` و`robot.stop()` و`robot.drive(speed, turn_rate)`، دون معاملات مسمّاة أو تعبيرات تنفيذية أو تعليمات إضافية.
- حدود الإدخال: مسافة ±10000 مم، دوران ±3600 درجة، ومعاملَا `drive` ضمن ±1000 بوحداتهما. هذه حدود تحقق **وليست ضماناً لسلامة الحركة**؛ راجع السرعات والمقاسات والمسار يدوياً، خصوصاً أن `drive` مستمر وغير حاجب.
- Esc يلغي العملية الجارية وينتظر تنظيفها ثم يرسل إيقاف البرنامج إن وجد اتصال. لا تغلق التطبيق كبديل عن زر الإيقاف؛ قطع الاتصال لا يعني إيقاف برنامج الروبوت.

اختبارات المنطق تعمل دون روبوت ودون تثبيت اعتماديات التشغيل، مع بدائل للواجهة والعتاد.
تشمل الاختبارات الجديدة خادم الويب كاملاً عبر HTTP (ملفات، إعدادات، تحقق صياغة، رفع
وتشغيل في وضع المحاكاة) وروبوت المحاكاة وجلسة التدريب، إضافة إلى فحوص ثابتة تتأكد من

ومسار API تستخدمه الواجهة. لتجربة بناء واجهة Tk على جهاز يدعم العرض:

```sh
python spike_controller.py --selftest
```

لمبرمج الكتل اختبارات مستقلة: `node tools/blocks_check.js` يتحقق من نموذج الكتل ومن
مولّد كود Pybricks (تطبيع المدخلات، الحدود، التوليد لكل نوع كتلة، تحرير الشجرة)، و
`tests/test_blocks.py` يتأكد من صلاحية الكود المولّد ببايثون (`compile`)، ومن حفظ ملفات
`.blocks` داخل مساحة العمل، ومن وجود نصوص الترجمة وربط الواجهة.

اختبارات CI مهيأة لـ Windows وLinux وPython 3.11–3.13. تُضاف على Linux اختبارات Tk فعلية عبر Xvfb للتحقق من ظهور اسم الملف عند أصغر حجم نافذة ومع أسماء طويلة وعربية، واستقلال المحررات والتراجع والتمرير والتلوين وإغلاق التبويبات؛ وتُتخطى هذه الاختبارات محلياً عند عدم توفر Tk أو شاشة عرض. تشمل الاختبارات أيضاً ضغط الأزرار والقوائم، مساحة المحرر عند 900×560 و1220×780 و1600×900، موضع الشريط الرفيع، ودقة تقدم الرفع والفشل والإلغاء وتجاهل رسائل العمليات القديمة. اختبارات BLE/USB/COM والحركة الفعلية تحتاج الجهاز والفرموير المستهدفين؛ الاختبارات المعزولة ليست بديلاً عنها.


## تشخيص خطأ GATT أثناء الإرسال (خصوصاً مع فرموير 4.1.0)

`BleakGATTProtocolError: (14, 'GATT Protocol Error: Unlikely Error')` لا يحدد سبباً واحداً، ولا يعني بمفرده أن ملف Python أو الفرموير يحتاج إلى استبدال. في مصدر فرموير 4.1.0 توجد مهلة نقل تبلغ ثانية واحدة تُجدّد مع وصول البيانات، وأخطاء حالة النقل قد تتحول إلى `0x0E`؛ لكن تعيين هذا السبب على جهاز معين يحتاج سجلاً واختباراً فعلياً:

- [مصدر تخزين البرامج في فرموير 4.1.0](https://github.com/pybricks/pybricks-micropython/blob/v4.1.0/lib/pbio/sys/storage.c)
- [تحويل أخطاء البروتوكول في فرموير 4.1.0](https://github.com/pybricks/pybricks-micropython/blob/v4.1.0/lib/pbio/src/protocol/pybricks.c)

إجراءات التطبيق الجديدة:

- يحد حجم كتابة حزم الرفع عبر BLE إلى **20 بايت** (تشمل ترويسة أمر Pybricks) لتفادي الحاجة إلى كتابة BLE طويلة على بعض المحولات. هذا يقلل السرعة، وهو إجراء توافق احترازي وليس علاجاً مضموناً لكل خطأ `0x0E`. لا يُطبق على USB ولا يعدّل Bleak عالمياً.
- ينتظر انتهاء البرنامج وحالة إدخال/إخراج الملفات، بمهلة محدودة، بدلاً من افتراض جاهزية الروبوت بعد نصف ثانية. في مسار BLE الحديث يشترط **تقرير حالة جديدًا** قبل الرفع وبعده، ويتجاهل القيمة المخزّنة التي تعيدها `BehaviorSubject` عند الاشتراك. فرموير 4.1.0 يعلّق إرسال إشعارات الحالة أثناء النقل؛ لذلك قد تبقى القيمة المخزّنة صفرًا رغم استمرار عملية نقل سابقة. لا ينتظر إشعارات بين حزم الملف، لأنها قد تكون معلّقة أثناء النقل نفسه.
- يفصل تنزيل الملف عن أمر تشغيله على الفرموير الحديث؛ لا يبدأ البرنامج إذا فشل الرفع، ولا يعيد أمر التشغيل تلقائياً إذا فشل إقراره.
- يمنع «تشغيل المخزن» بعد فشل رفع أو إلغائه حتى يكتمل رفع جديد بنجاح خلال جلسة التطبيق الحالية.
- يعرض رسائل ASCII واضحة، منها `phase=stop-ready` و`phase=compile-upload` و`phase=upload-ready` و`phase=start`؛ في وضع انتظار نهاية البرنامج تظهر `phase=start-wait`.
- يسجل إصدار الفرموير و`pybricksdev` و`bleak`، ويحفظ الاستثناء الكامل في `logs/transfer_errors.log` داخل **مجلد بيانات المستخدم** الموضح أعلاه.
- عند فشل كتابة رفع BLE يضيف سطرًا مثل `[TX] upload command=data offset=45 ...`: يحدد `begin` أو `data` أو `finalize`، وحجم الحزمة والحمولة والبايتات التي تم تأكيدها (`acked_bytes`) وأزمنة الكتابة والفجوات بين الكتابات بالمللي ثانية. `cached_flags` حالة مخزّنة وليست قراءة مؤكدة للحالة الحالية. لا يسجل محتوى البرنامج ولا يضيف طباعة لكل حزمة، ولا يغيّر تأطير المكتبة أو يعيد الكتابة الفاشلة تلقائيًا. أزمنة تقارب ثانية أو تتجاوزها تستحق الفحص بسبب مهلة خمول النقل في 4.1.0، لكنها ليست وحدها إثباتًا للسبب على الجهاز.
- حجم 20 بايت **ليس مثبتًا كسبب الخطأ**؛ ينتج عنه 15 بايت بيانات بعد ترويسة الأمر ذات 5 بايت. هذه مهلة خمول بين البيانات، وليست حدًا قدره ثانية واحدة لمدة رفع الملف كاملًا. تفاصيل المراجعة ومصادر الفرموير في [`reports/ble_transfer_review.md`](reports/ble_transfer_review.md).

إذا استمر الخطأ، أغلق اتصال Pybricks Code وأي تطبيق آخر متصل، ثم أعد الاتصال. بعد حفظ تسجيل التدريب المهم، جرّب ملفاً بلا حركة مثل `print("SPIKE OK")` وأرسل أسطر `[TX]` وملف `transfer_errors.log`. لا تعد تثبيت الفرموير بناءً على هذه الرسالة فقط. حدود الحزم وانتظار الجاهزية مختبرة برمجياً، لكن نجاح النقل الفعلي يحتاج تجربة على الـHub ومحول البلوتوث المستهدفين.
